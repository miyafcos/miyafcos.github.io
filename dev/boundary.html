アプリと外側の境界

mycmux のアプリと外側は、4 つのインターフェースでつながっています。外側とは、Claude Code、Codex、Grok といったエージェント製品とその設定ファイル、そして作者の運用のことです。作者の運用は、~/.claude にある skill、hook、スクリプト、台帳を指します。

  1. socket（アプリが localhost で待ち受ける）と、それを包む CLI と bridge
  2. hook（アプリがエージェントの設定ファイルに書き込んで登録し、エージェントが自分の状態を知らせる）
  3. PTY に渡す環境変数
  4. 同梱のスキルパック（アプリが skill と CLI を配布する）

4 つとも動いていますが、依存の向きは一方通行ではありません。アプリはエージェントの設定、認証、信頼のファイルを書き、skill はリポジトリの作業ツリーにある CLI を直接呼びます。版のずれや片側だけの変更が、もう片側を黙って壊しうる箇所は 20 か所ありました。

mycmux は、最初はターミナルを並べるだけのエディタでした。8 月以降に委譲タスク、判断カード、hook、アカウント切替などを取り込んだ結果、アプリと作者の運用の両方にまたがる仕組みが増えています。

作者は、mycmux が「ハーネスで管理すべきことと、アプリとして管理すべきことの両方を抱えている」と見ていました。ここでいう「ハーネス」は作者の運用（skill、hook、スクリプト）のことです。業界の用法とずれるので、以降は部品の名前で呼びます。

以下では、どのインターフェースを何が通っているかを追いながら、その見立てを確かめます。その後に作者が決めた立ち位置は、立ち位置と約束に書きました。

3 つの領域と 4 つのインターフェース#

矢印は、書き込みやコマンドの向きを表します。② hook の矢印は、アプリがエージェントの設定ファイルに hook を登録する向きです。登録した hook からの申告はエージェントからアプリへ向かい、① と同じ socket を通って届きます。

領域中身主な置き場
アプリRust（Tauri）とフロント（React）。ワークスペース・タブ・ペイン、PTY、保存、観測、表示~\cmux-for-linux-dev-master、%APPDATA% の下のアプリのフォルダ、~/.mycmux/
エージェントの設定と作者の運用Claude Code・Codex・Grok の設定ファイルと、作者の skill・個人の hook・スクリプト・台帳・rules ~/.claude/、~/.codex/、~/.grok/、%USERPROFILE%\claude-ops\
インターフェース両方にまたがる部品。socket と CLI・bridge、hook の helper、環境変数の約束、スキルパックscripts/mycmux_agent_cli.py、~/.mycmux/hooks/v1/mycmux_hook.py、skills/claude/

インターフェース 1: 制御 API（socket）#

socket は 127.0.0.1 の TCP 接続 1 本で、1 行に 1 つの JSON でコマンドを送ります。ポート番号は ~/.mycmux/mycmux.port、トークンは ~/.mycmux/mycmux.token にあり、どちらもアプリを起動するたびに作り直されます。loopback 以外からの接続は捨てます（src-tauri/src/socket.rs:1036-1089）。

トークンは 2 種類あり、それぞれ受け付けるコマンドの範囲（realm）が違います。

範囲トークン使えるコマンド利用側
一般（broad realm）アプリの起動ごとのトークンhook 以外のすべてCLI・bridge・pocket・2 個目の mycmux
hook（hook realm）エージェントの起動ごとに発行する使い捨ての hook 用トークン hook_cap hook.health・hook.observe だけhook の helper

両方のトークンを付けた要求は拒否され、一般の範囲からは hook.* を呼べません（src-tauri/src/socket.rs:180-208）。

コマンドは、Rust が直接答えるものが 8 系統、フロントに転送して答えるものが 47 個（正式名 39、旧名 8）あります。

系統主なコマンド応答する側主な呼び出し元
hook hook.health・hook.observe Rust hook の helper
状態session.state_view（ペインの状態の一覧）・status.subscribe（変化の購読）Rust CLI の status・bridge・pocket
トークンの発行launch.issue_hook_cap Rustランチャーのシェル関数
開くapp.open_paths・app.activate（リポジトリの最新の版で追加）Rust 2 個目に起動した mycmux
ワークスペースworkspace.list・workspace.new・workspace.closeフロントCLI
ペインpane.list_all・pane.spawn_tab・pane.send_text・pane.read・pane.close_tab ほかフロントCLI・bridge・pocket・session-dispatch の委譲
Web ペインweb.open・web.read・web.push ほか 19フロントoracmux
使用量account.usageフロントCLI・作者の birdseye スクリプト

フロントで答えるコマンドは主窓（リーダー窓）だけが実行し、30 秒以内に応答がなければ打ち切ります。同じ処理関数 handleSocketCommand は、アプリの画面自身も内部 API として 6 か所から呼んでいます。入力欄、返信欄、ペイン整理、WorkOrder などです。外向きの約束を変えると、画面の挙動も一緒に変わるということです。

段 1 で、稼働中の本体が版とコマンドと能力を返す system.version を加えました。CLI は、全件の status や起動指定に必要な能力を送信前に確かめます。能力が足りなければ操作せずに止まります。

CLI mycmux_agent_cli.py#

scripts/mycmux_agent_cli.py は、socket のコマンドを 1 つずつ送るだけの薄いクライアントです。session-dispatch の委譲は、この CLI を通して子セッションのペインを立てます。

サブコマンド送るコマンド既定の動きと約束
spawn --target <種類> pane.spawn_tab呼び出し元と同じタブにペインを足し、裏で起動する。新しいタブを割るのは --split を付けたときだけ。--workspace などを --split なしで付けるとエラー
spawn-tab pane.spawn_tab起動する種類（--target）かコマンド（-- 以降）のどちらか一方を指定
send --session pane.send_text --text だけなら Enter なし。--enter は Enter を 1 回送り、確認できなければ「不明」を返す。--key enter も 1 回
read、close-tab、rename、move pane.read ほか宛先はペインの PTY セッション ID
status session.state_view全件では null を認め、送信の期待値には整数だけを使う
workspace-new、workspace-close workspace.new、workspace.close前面のワークスペースは閉じられない
web-* web.* Web ペインの操作
version system.version稼働中の本体の版、コマンド、能力を照会する
hooks-status agent.hooks.status hook の導入状態を読み取るだけ

--target で選べる種類は 9 つあります。claude、codex、claude-codex、grok、agy、hermes、omp、shell、web です。

CLI の status（全件）は、入力改訂番号の null を認めるように直しました。null は送信の期待値には使えません。別リポジトリの pocket に移植された検査は、別途確認が必要です。

--model と --effort は、プロンプト、引き継ぎ、再開の経路にも渡します。適用できない対象や再開の組み合わせは、ペインを作る前に断ります。起動の応答は求めた値と渡した値を返しますが、製品への適用は未観測です。

インターフェース 2: hook の申告と使い捨てのトークン#

hook は、「質問を出した」「ターンを終えた」といった出来事をエージェント自身が知らせる仕組みです（それぞれの意味は観測とカード）。アプリの導入処理は、製品ごとの入切の設定に従って次のファイルを扱います。

書く先中身
~/.mycmux/hooks/v1/mycmux_hook.py helper 本体（exe に埋め込んだものを書き出す）
~/.claude/settings.json Claude の 7 イベント（UserPromptSubmit・PermissionRequest・Notification・PreToolUse・PostToolUse・Stop・SessionEnd）に helper を登録
~/.codex/hooks.json Codex の 4 イベント。~/.codex/config.toml の信頼のハッシュ（trusted_hash）を照合し、未承認なら Codex の分だけ登録しない
~/.grok/config.toml Grok の 5 イベントを中身で識別し、自分の重複を整理する

設定画面の「エージェント連携」で、製品ごとに状態を見て、入れる、直す、外すを選べます。外した設定は起動時にも守られます。

  1. ランチャーで起動
  2. トークンを発行
  3. 子プロセスだけに渡す
  4. helper が申告
  5. 受付で検査

エージェントを起動するたびに、ランチャーのシェル関数（claude、codex、grok などをラップしたもの）が socket の launch.issue_hook_cap を呼びます。受け取った使い捨てのトークンは、環境変数 MYCMUX_HOOK_CAP に入れて、その 1 回の起動にだけ渡します（src-tauri/src/launcher.sh:88-128）。helper は、トークンがなければ何もせずに終了します。

トークンを配るのはランチャーのシェル関数だけで、Rust はこの変数を消すだけです。ところが再起動後の復元のように、アプリがランチャーを通さずにエージェントを直接起動する経路もあります。コードを読む限り、この経路では hook が何もせずに終わります（実機では未確認）。ADR 0009 が想定した注入の位置（Rust の起動処理）とも違っています。

hook の導入まわりで見つかった問題は、次の 4 つです。

  1. Grok の重複を整理する処理。段 1 で、呼び先と mycmux_managed から自分の hook を識別するように直しました。調査時点の実設定は 5 組でした。初回起動後に実設定が 1 組になったかを確認します
  2. 作者の設定の正本を書き換える。作者のホームにある CLAUDE.md は、settings.json の hooks を「慎重に扱う」対象にしています。それなのにアプリは、差分があれば毎回書き換えます（同時の編集は照合して拒否する作り）
  3. helper の改行コード。リポジトリは LF、書き出された helper は CRLF です。別の checkout からビルドした exe を交互に起動すると、そのたびに書き直されます
  4. テスト用インスタンス。テストプロファイルでは hook を導入しませんが、live の設定が指す helper は MYCMUX_RUNTIME_DIR を読みます。そのため、テスト用インスタンスの中で動くエージェントの申告は、そのインスタンスの socket に届きます

インターフェース 3: PTY に渡す環境変数#

アプリは PTY に、そのペイン自身の ID や成果物の置き場などを環境変数で渡します。一方で、resume、引き継ぎ、起動対象といった一度きりの指示が別のペインや次の起動へ漏れないよう、4 か所で変数を消しています。きっかけは 5 月の版で起きた事故です。Ctrl+P の環境変数が他の PTY へ漏れ、新しいペインが勝手に resume されました（CHANGELOG.md:2046-2052）。

場所いつ何を消すか
src-tauri/src/lib.rs:305-330 exe の起動時に、自分の環境から20 キー
src/lib/spawnLaunchEnv.ts:3-35新しいペインを作るときに、親ペインの環境から20 キー
src/components/layout/SocketListener.tsx:1078-1101 data.json に保存する前18 キー
src-tauri/src/commands/terminal.rs:680-755（sanitize_launch_env）PTY の起動直前17 キー。resume は ID と種類が揃うとき、引き継ぎは種類と元のペインが揃うときだけ残す

消したあとで、アプリが正しい値を入れ直します（MYCMUX_PANE_SESSION_ID、MYCMUX_RUNTIME_DIR、MYCMUX_TAB_ID、成果物の出力先など）。4 か所には同じ文字列の並びを 4 回書いてあり、契約テスト tests/test_ephemeral_env_keys_contract.py で一致を保っています。リポジトリの CLAUDE.md には「3 層」とありますが、いまは 4 か所です。

作者の個人の hook も、この環境変数を読んでいます。ask-inject.py と、子セッションの質問を止める hook（dispatch-child-guard.py）は、MYCMUX_PANE_SESSION_ID と委譲の台帳から「自分は子セッションか」を判定します。アプリがこの変数の付け方を変えると、hook の判断も黙って変わります。

インターフェース 4: スキルパック（skill の配布）#

アプリは 3 つの skill と CLI を exe に埋め込み、アプリのリリースとして配布しています。skill は session-dispatch、mycmux-bridge、oracmux です。ほかの PC でも ~/.claude/skills/ と ~/.mycmux/bin/ に導入できるようにするためで、導入は「設定 → AI → Claude Code スキル」から行います。

  1. 保守者が python scripts/sync_claude_skills.py --from-live --write-manifest を実行し、live の skill を持ち運べる形（個人のパスを置き換えたもの）に変換してリポジトリに入れる
  2. ビルド時に exe へ埋め込む（src-tauri/build.rs:40-80）
  3. 利用者が設定画面から導入する

調査時点では、パックと live の中身は一致していました（--check は exit 0）。ただ、調査した PC は保守者のもので、live が原本なので導入済みの記録がありません。このため設定画面は、3 つとも「ローカルで改変済み」と表示します。

ここで「退避して置き換える」を押すと、原本が持ち運び版で上書きされます（押してはいけません。コードからの推論です）。~/.mycmux/bin/mycmux_agent_cli.py は 9 月中旬の版のままで、どこからも参照されていません。

作者の個人の hook の一覧#

Claude の hook は、10 イベントに 22 個が登録されています。表の中の注記は次の意味です。

  • 「（mycmux）」は、アプリが入れた mycmux の hook
  • 「（mycmux 前提）」は、mycmux があることを前提に動く作者の個人の hook
  • 「（二重記録）」は、アプリと同じ出来事を別に記録しているもの
イベント呼ぶもの目的
UserPromptSubmit hooks_dispatch.py から prompt-secret-guard、rule-drift-guard、session-inject（mycmux 前提）、ask-inject（mycmux 前提）、ターンの記録（二重記録）秘密の遮断、文脈の注入、判断カードの注入
UserPromptSubmit feedback-injector、skill-hint-injector、turn_active（mycmux）feedback と skill の候補、ターン開始の申告
PreToolUse risk-guard、agent-model-guard、comms-search-guard、dispatch-child-guard（mycmux 前提）、pre_tool_use（mycmux）危険な操作の拒否、子セッションの質問の遮断、ツール使用の申告
PostToolUse checkpoint、slack-log、skill_usage、turn_active（mycmux、AskUserQuestion の後）途中経過の保存、使用記録
Notification、PermissionRequest通知の記録と notify.ps1（二重記録）、attention_required（mycmux）通知
SessionStart resume-inject（mycmux 前提）、compact-reinject、掃除とトークン更新前回の文脈の注入
Stop session-summarize、daily-log、ターンの記録（二重記録）、turn_ended（mycmux）要約、日報
SessionEnd session_terminated（mycmux）終了の申告

Codex の自前の hook は、SessionStart の通知と Stop の入口です。Stop から消えた収集スクリプトを呼ぶ処理は外しました。残りの 4 つは mycmux のものです。Grok には mycmux の hook しかありません。

作者の Codex Stop hook から、消えた収集スクリプトの起動を外しました。Codex の hook 設定の並びは変えていません。これは作者の環境側の修正です。

bridge の安全な送信#

mycmux-bridge（作者の skill）は、別のペインへ取り違えや二重送信なしに入力するための道具です。委譲タスクへの追加指示（dispatch_send.py）も、これを使っています。

  1. 宛先を解決し、session.state_view で、ペインが生きているか、attention が期待どおりかを確かめる
  2. 画面を読んでフィンガープリントを取り、状態と画面をもう一度取り直す。変わっていたら何も書かない
  3. 本文を、期待値 4 点（epoch、attention id、セッション改訂番号、入力改訂番号）付きで書く。Rust が事前に照合し、最後に write_to_session_guarded がすべてを照合してから書き込む
  4. 入力欄に本文が表示されるまで待ち、状態と画面を確かめ直してから、Enter を 1 回だけ送る
  5. 入力欄から本文が消え、画面か状態が変われば「届いた（observed_delivered）」とみなす

送信の安全策は 3 か所に分かれています。段 1 で CLI の Enter も 1 回にそろえました。受理を確かめられなければ「不明」を返し、自動で押し直しません。

bridge は、リポジトリ作業ツリーの CLI をモジュールとして読み込んでいます。そのため、別のセッションが CLI を未コミットのまま編集すると、その変更がすぐ skill に効きます。

どちらが何を知っているか#

アプリだけが知っていること#

skill がこれらを知るには、socket で問い合わせるしかありません。

事柄skill からの見え方
ワークスペース・タブ・ペインと PTY の対応、前面の窓pane.list_all
ペインの状態（生死・動き・attention・改訂番号）session.state_view・status.subscribe
ペインの画面pane.read
どの起動が現行か・発行したトークン・hook の受理と拒否の数見えない
稼働中の exe の版と使えるコマンド問い合わせる手段がない

作者の運用だけが知っていること#

事柄アプリからの見え方
委譲タスクの親子関係・spec・状態（台帳）委譲の見守りが古い規則で読んでいるだけ
判断カードの待ち行列知らない
見張りを止めたことランチャーが環境変数を見て、見張りを起こすのを省くだけ
委譲の規則・モデルの割り当て知らない
個人の hook がしたこと（拒否・遮断・注入）見えない

両方が別々に記録していること#

事柄アプリ側作者の運用の側
ターンの始まりと終わりhook.observe %USERPROFILE%\claude-ops\state\agent-turn-events*.jsonl（読む側が見つからない）
通知Notification hook から attention へnotify.ps1 と agent-notifications.jsonl
Claude のフォルダの信頼（~/.claude.json）起動のたびに書くdispatch_preflight.py も書く
resume data.json と CLI の --resume作者の環境には直した resume-inject を入れ済み。本体の更新後、再開と引き継ぎでは注入を省く
CLI の置き場同梱版を ~/.mycmux/bin へリポジトリ作業ツリーを直接指定（8 か所以上）
エージェントの種類の一覧追跡は 4 種、起動は 7 種CLI 9、bridge 5、helper 3、ランチャーの case 文
状態の応答の検査Rust の型CLI と bridge は null を認める。pocket の検査は別途確認が必要
委譲タスクの終了状態の集合Rust と TS に写しがあるdispatch_ledger.py。3 者を突き合わせるテストはない

境界の食い違い（20 件）#

調査メモで、下の 20 件とは別に Codex の Stop hook の問題も見つけました。作者の環境側で消えたスクリプトの起動を外しました。こちらは既知の問題の 22 番にも載せています。どの領域に置き直すかは、立ち位置と約束にあります。

  1. hook 用トークンを配るのがランチャーだけなので、アプリが直接起動したペインでは hook が効かない（推測）
  2. 調査時点で Grok の設定に hook が 5 重に入っていた。段 1 の導入処理で整理する
  3. アプリがエージェントの設定と信頼を書く。段 1 で hook の入切と状態を見せる画面を加えた
  4. ~/.claude.json の信頼を、アプリと dispatch_preflight.py の 2 者が書く
  5. skill は作業ツリーの CLI を使う。段 1 で必要な能力を稼働中の本体に照会するようにした
  6. CLI が 2 つある（リポジトリ版と ~/.mycmux/bin 版）
  7. ~/.claude/scripts/codex-visible.py がトークンなしで socket を呼ぶ。そのため 8 月上旬に認証が入ってからは可視ペインを立てられず、黙って画面なしの codex exec に切り替わる。それでも codex-helper と delegation-playbook は、この経路を案内している
  8. CLI の status（全件）は、段 1 で null を認めるように直した
  9. 送信の安全策は 3 か所に分かれる。段 1 で CLI の Enter は 1 回にそろえた
  10. --model と --effort は、段 1 で起動の各経路へ渡すように直した
  11. socket のコマンド表が、フロントの内部 API を兼ねている
  12. アプリのランチャーが、エージェントを起動するたびに見張りのスクリプトを起こそうとする
  13. ターンと通知の記録が 2 系統あり、個人の hook の側の記録は誰も読んでいない
  14. 委譲タスクの終了状態の集合が、Python、Rust、TS に 3 重に定義されている
  15. 個人の hook が、アプリによる環境変数の付け方に依存している
  16. リポジトリのテストが、作者の live の bridge を読み込んで試験している（tests/test_mycmux_bridge.py:13-24）
  17. 文書が古い（docs/agent-integration.md、socket の説明文書に 13 系統の記載がない、CLAUDE.md の「3 層」）
  18. 保守者の PC で設定画面の「置き換える」を押すと、原本が持ち運び版に置き換わる
  19. 呼び出し元のないコマンドがある（旧名 8、workspace.select は何もしない、pane.launch_declared は設定でオフ）
  20. 実際に使われているのは launcher.sh なのに、agy の配色対策（NO_COLOR）は launcher.ps1 にしか入っていない
