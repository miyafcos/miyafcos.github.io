委譲便とは、親が別のペインに新しいセッションを立てて仕事を出し、回収するまでの 1 回分です。これを組み立てているのはハーネスで、アプリは spawn、send、read、close の「器」を貸しているだけです。アプリは、便という概念を持っていません。

アプリ側にある「委譲の見守り」は、ハーネスの台帳を古い読み方で読んでいます。いまの便の形では、ほとんど通知が出ないと見ています（推測、通知の件数は未計測）。見張り（dispatch_guard.py）は、9 月中旬から意図的に止めてあります。判断カードは、9 月中旬以降の 22 枚がすべて子から出たもので、うち 21 枚が解決しました。

このページでは、ディスパッチ（親から子への委譲）の仕組みを、ハーネス側とアプリ側に分けて説明します。親（作者と話している Claude のセッション）は、重い作業を子（親が別のペインに立てた新しいセッション）に出します。そうすると親の文脈（会話の履歴）が軽いまま保て、並列に回せます。

記録は、7 月末に始まった台帳（ledger.jsonl、便を 1 行ずつ残すファイル）にあり、調査時点で 453 便あります。8 月から 9 月にかけて、ハーネス側の読み方と見張りが何度か作り直されました。そのため、アプリ側の実装や文書との食い違いが残っています。

このページの目的は、いまどこが生きていて、どこが食い違っているかを 1 か所にまとめることです。ハーネス側のファイルは、session-dispatch skill の中の相対パス（SKILL.md、scripts/…）か、~/.claude/ からのパスで書きます。

1 便の流れ

図の読み方です。「CLI で spawn」の枠が、ハーネスがアプリの器（socket）を使う境目です。

  1. 振り分け
  2. spec を書く
  3. preflight
  4. spawn
  5. 台帳に記録
  6. 作業と追加指示
  7. 完了の回収
  8. 片付け

振り分けは、session-dispatch skill の判定表で行います。選択肢は 5 つです（~/.claude/skills/session-dispatch/SKILL.md:22-34）。「親のまま」「Codex に委譲」「新しいペインの Claude」「分割（上限 3 本）」「Agent ツール」です。新しいペインを使うと決めたら、次の順に進みます。

  1. spec（子への初回指示書）を書く。置き場は、便フォルダ ~/.claude/dispatch/<YYMMDD>-<名前>/ です。必須項目は 5 つで、変更してよい範囲、完了の条件、接続先、判断者と完了報告（DONE）の約束、判断カードの約束です（skill の references/spec-template.md:8-54）
  2. preflight を走らせる。子の作業フォルダを信頼済みにし、MCP 2 つ（相談用の MCP と deepwiki）を ~/.claude.json に書きます。外部サービスの経路も確かめます（~/.claude/skills/session-dispatch/scripts/dispatch_preflight.py:28-72）。最後に見張りの ensure() を呼びますが、見張りは止まっているので空振りします
  3. spawn する。mycmux_agent_cli.py spawn --target claude --prompt-file <spec> --label <名前> --no-activate を使います。既定では呼び出し元と同じタブの裏ペインになり、別のタブに分けたいときだけ --split を付けます（scripts/mycmux_agent_cli.py:478-497）
  4. 台帳に記録する。dispatch_ledger.py append が、spawn の応答の sessionId を tab_session_id に写します。tab_session_id は、そのペインの PTY セッション ID で、送信と片付けの宛先です。直近 7 日の 119 便すべてに、この値が入っています
  5. 作業と追加指示。追加の指示は、dispatch_send.py で送ります（後述）
  6. 完了の回収。子は DONE*.md を書きます。親はその自己申告をそのまま信じず、成果物を自分で確かめます
  7. 片付け。close-tab --session <tab_session_id> でペインを閉じ、台帳を closed にします

実例: 調査当日の 1 フォルダ 3 便

調査当日のある便フォルダには、3 便（openwith、perf1、perf2）が入っていました。子はすべて Codex で、作業フォルダはそれぞれ専用の git worktree です。記録の形だけを、時刻順に並べます。

  • 12:59 親が spec_openwith.md と prompt_openwith.txt（spec を全文読めという英文 1 行）を書く。spawn の応答を spawn_openwith.json に保存
  • 13:00 台帳に openwith の行。target は codex で、model（GPT-6 世代）と effort（xhigh）は記録のみ
  • 14:08 子が DONE_openwith.md を書く
  • 14:17 親が差し戻しの spec_openwith_fix1.md を書く（届け方は記録から追えない）
  • 14:28 台帳の openwith を closed に
  • 17:37 子が DONE_perf1.md を書く。アプリの編集保存が .bak を 2 本残す
  • 17:40 親が STATUS.md（現在地メモ）を書き、perf2 を open に。17:44 に待ち受け用の poll_seat.py を置く

この例では、自動検収の VERDICT.md も判断カードも作られていません。親は watcher を使わず、便ごとに待ち受けのスクリプト（wait_done.py、poll_status.py、poll_seat.py）を書き直しています。

手順書（SKILL.md）は、「1 フォルダ 1 便・固定名 spec.md と DONE.md」を前提にしています。実運用では、1 フォルダに複数のレーンを置き、ファイル名にレーン名を付けています。直近 7 日の DONE 96 件のうち、固定名の DONE.md は 44 件だけでした。

追加指示の送信

dispatch_send.py は、次の順で子に指示を届けます。自動の再送はしません。

  1. 宛先を台帳から 1 便に絞り、その tab_session_id を使う。閉じた便なら送らない
  2. アプリの session.state_view から、期待値 4 点（epoch、attention id、セッション改訂番号、入力改訂番号）を取る
  3. 既定では、子に注意の印（attention）が付いていないことを求める
  4. 本文を入れ、自分の入力で進んだ入力改訂番号を追ってから、Enter を 1 回送る。アプリ側は、期待値が一部だけなら incomplete_expectations で拒否する（src/components/layout/socketCommands.ts:2053-2057）
  5. Enter のあと 20 秒、入力欄が空になり、状態か transcript（会話の記録ファイル）が動くかを見る
  6. 確かめられなければ、guard/pending_sends.jsonl に「見張りに任せる」として登録する

送信の結果は「配送を観測できた」までで、子が指示を実行した証明にはなりません。確かめられなかった送信の登録は 123 行あり（調査時点）、未解決のまま 51 セッション分が残っています。見張りが止まっているので、この登録は誰にも拾われません。

完了の回収

dispatch_watch（自動検収）

DONE.md を見つけると spec の検収ブロックを実行し、全部通れば close-tab して台帳を閉じます。固定名の spec.md と DONE.md しか見ないため、1 フォルダ複数レーンの便には使えません。VERDICT.md は直近 7 日で 6 件でした。

dispatch_status（状況表示）

子の Claude の transcript 1 本の更新時刻で、「動いている / 止まっている」を決めます。Codex の子と専用 worktree の子は読めません。157 行中 97 行が UNKNOWN で、うち 95 行は Claude のプロジェクトフォルダが無いものでした。

実運用: 親の自作ポーリング

便フォルダに wait_done.py、poll_status.py、poll_seat.py などを置き、DONE の出現や、画面の質問、使用量上限を見て止まります。便ごとに書き直しています。

判断カード

判断カードは、走っている子が人の判断を求めるための、唯一の正規の経路です。子が自分で AskUserQuestion（Claude Code の選択式の質問ツール）を出すと、親に届かずに画面で止まってしまいます。そのため hook（Claude Code がツールを使う前後に呼ぶスクリプト）で止め、カードに回します。

図の読み方です。「遮断」の段は hook が止める段、「判断」の段は人（作者）の判断です。戻りの矢印は、回答を受けて子が作業に戻ることを示します（再び質問するという意味ではありません）。

  1. 子が AskUserQuestion、EnterPlanMode、ExitPlanMode を呼ぶと、PreToolUse hook の子の質問封じが拒否する。判定は「自分のペインの ID が台帳にあり、閉じた便ではない」（~/.claude/skills/session-dispatch/scripts/*-child-guard.py:94-132）。拒否の文面は「推奨案で続行し、本当に止まるときだけカードを出せ」。拒否の記録は 66 行（9 月上旬から調査時点まで）
  2. 子は便フォルダに card.json（題、問い、補足、選択肢と推奨、推奨の理由、止まる理由、判断の種類）を書き、ops_common.py enqueue でキューに入れる
  3. 入口で機械検証する。問いは 120 字以内の 1 文、選択肢は 2〜4 個で各 20 字以内、推奨はちょうど 1 つ。「上記」「ログを見」のような文脈頼みの語は不可（~/.claude/ops/ask_validation.json）
  4. 親の次のプロンプト送信のたびに、UserPromptSubmit hook から ask-inject.py が動く。その子を出した親あての未回答カードを、最大 3 枚会話に差し込む。調査当日の 1 日で 1,020 回動き、所要時間の中央値は 203 ミリ秒
  5. 親が作者に聞き、明示の判断を得てから、ops_common.py answer-ask を 1 回だけ実行する。回答は mycmux_agent_cli.py send --enter で子に届き、90 秒以内に子の再開を観測できれば解決になる

9 月中旬以降の 22 枚のうち、21 枚が解決しました（残る 1 枚は診断用）。

キューには、8 月上旬から 282 枚が積まれています。257 枚は見張りが出したもので、236 枚が却下されました（そのうち 158 枚は「止まっていなかった」）。

見張りを止めた 9 月中旬より後は、子が出したカードだけになりました。判断の種類は、権限と安全 9、外部への反映 7、持ち主の判断 3、要件の衝突と不可逆と範囲の変更が各 1 でした。Codex の子が出したカードは 0 枚です。

answer-ask は、実質的に期待値なしで送っています。期待値はカードを積むときに panes --all から取る設計ですが、アプリの pane.list_all はその欄を返しません（src/components/layout/socketCommands.ts:647-706）。9 月中旬以降の 22 枚で、期待値が保存されたカードは 0 枚でした。

さらに、送信の 3 秒後に空の Enter をもう 1 回送ります。子がすでに次の質問を出していた場合に、それへ答えてしまう余地があります（推測）。

clone_draft は、作者の判断の一次案を別の skill に作らせ、カードに添える仕組みです。skill とエージェント定義には書いてあります。しかし、カードを受け付ける cmd_enqueue は読む項目が固定で、clone_draft を捨てます（~/.claude/ops/ops_common.py:1426-1500）。便フォルダのカード 12 個とキューの 282 枚のどちらにも、clone_draft は 1 件もありませんでした。

見張り dispatch_guard（休止中）

見張りは、子や手動のエージェントのペインが黙って止まるのを検出し、回復させるか通報する常駐プロセスです。止まる原因として、起動時の確認、入力欄に残った本文、質問、承認、ログインを見ます。9 月上旬に入れ、9 月中旬に止めました。

止め方中身
DISABLED ファイル~/.claude/dispatch/guard/DISABLED（9 月中旬）。止めた理由が 2 つ書いてある。「カードが雑音だった」と「カードに答えると回答文が無関係なペインに打ち込まれた」で、再開の手順も書いてある
ユーザー環境変数MYCMUX_DISPATCH_GUARD=off。ランチャーが見張りを起こすのを止める
スケジュールタスクClaudeOps-DispatchGuard は 9 月上旬から無効。10 分ごとの起動を 2,204 回飛ばしている

止める前の見張りは、15 秒ごとに画面を 40 行読んで、13 種類に分類していました。読む対象は、Claude、Codex、Grok の全ペインと、台帳の子です。処置は、キー送出、推奨の選択肢での回答、承認の拒否、催促、lost の付与、通報です。通報の記録は 1,150 行（9 月上旬から中旬）で、そのうち 879 行は「ペインが消えた」でした。

止めたあとも、dispatch_send.py、dispatch_preflight.py、dispatch_watch.py が、見張りの ensure() を関数として直接呼びます。そのたびに見張りのプロセスが立ち、DISABLED を見て即終了し、guard.log に 1 行残します（調査時点で 165 行）。開発の記録にある「9 月上旬に dry-run で停止」は古い記述です。9 月中旬の停止の直前は、本番モードで動いていました。

アプリ側: 委譲の見守り

設定画面の「委譲の見守り」は、Rust の dispatch モジュールが担う機能です。主窓が見えている間、10 分ごとにハーネスの台帳を読み、質問待ち、完了未確認、停滞をトーストで知らせます。送信も片付けもしません（契約テスト tests/test_dispatch_watchdog_contract.py:28-36）。担当の窓は、ハーネスの置き場に書く .watchdog.lock で 1 つに決めます。

台帳の読み方が、ハーネスの決まりと 3 点で食い違っています。

食い違いアプリの読み方ハーネスの決まり
便のまとめ方slug ごとに、行を後勝ちで重ねる（src-tauri/src/dispatch/ledger.rs:54-72）。経過時間も、最後の行の時刻から測る同じ slug の別の便は混ぜない（8 月中旬に改めた）
動いているかの判定作業フォルダに対応する Claude のプロジェクトフォルダの、最新の jsonl の年齢（src-tauri/src/dispatch/ledger.rs:74-92）親や兄弟の活動と取り違えるので廃止（~/.claude/skills/session-dispatch/scripts/dispatch_status.py:5-7）
完了と質問のファイル固定名の DONE.md、ASK.md、VERDICT.md だけを見る（src-tauri/src/dispatch/ledger.rs:117-119）完了は、レーン名付きの DONE が過半。質問はカード（ops キュー）で、ASK.md は 9 月中旬を最後に使われていない

トーストになるのは、「質問あり（ASK.md）」「検収で不合格」「入力が残ったまま」の 3 種だけです。調査当日の例のように、Codex の子で専用 worktree を使う便は、「ログなし」のまま 3 時間たつと timeout になります。この種類は、トーストになりません。

アプリ側: WorkOrder と自動化スイッチ

WorkOrder は、契約カードから統合役のペインを 1 本立てる仕組みです。契約カードは、ダッシュボードの入力欄で 2 つ以上のペインを @ で指し、「まとめる・統合する・比較する」と書くと出ます。材料役のペインの要約を集め、git worktree を用意し、計画を封印（seal）してから、socket と同じ pane.spawn_tab を呼びます（src-tauri/src/workorder/executor.rs:180-236）。

コードは端から端までつながっていますが、~/.mycmux/workorders.db には 8 月中旬の下書きが 1 件あるだけで、GO（実行）は一度もありません。この DB は 192MB ありますが、中身の大半は別の機能の観測台帳です（agent_state_ledger 93,924 行、agent_state_observations 94,374 行）。

設定の「自動化」タブにある 2 つのスイッチ（自動で次へ進む、注意カード）は、既定値のまま一度も保存されていません。この「注意カード」はアプリのカードのスイッチで、ハーネスの判断カードとは関係ありません。

境界の食い違い

ディスパッチで見つかった、ハーネスとアプリの責務の重なりと食い違いです。どちらに寄せるかの提案と設計上の論点は、責務の分け方にまとめています。

  1. アプリがハーネスの台帳を、ハーネスがやめた規則で読んでいる。形式が変わっても、アプリのテストは固定の写しと比べるだけで気づかない
  2. 書き込みが双方向に越境している。アプリはハーネスの置き場に .watchdog.lock を書き、ハーネスの codex-visible.py はアプリの置き場 ~/.mycmux/agent-jobs/ に書く
  3. アプリのランチャーが、ハーネスの常駐プロセス（見張り）を起こす。止める手段は 3 か所に分かれている。スキルパックを配った先の環境では、既定で動く
  4. 停止の検知が 4 系統ある（見張り、委譲の見守りと停滞検知、/seats、親の自作ポーリング）。どれが正本か決まっていない
  5. 「カード」が 2 系統ある。ハーネスの判断カード（ops キュー）と、アプリの注意カード（workorders.db の attention_cards）で、互いを読まない
  6. answer-ask が、アプリの楽観ロック（期待値つき送信）の約束を迂回している
  7. 委譲の記録が 2 つある（ハーネスの台帳と、アプリの WorkOrder）。どちらも同じ pane.spawn_tab で子を立てるのに、互いを知らない
  8. model と effort は、記録と効果がずれている
  9. 委譲の契約の正本とされる docs/agent-integration.md が、見張りを稼働中として書いている
  10. 活動の判定が Claude 専用で、Codex の子（直近 7 日で 29 便）は読めない
  11. 質問の経路が 3 つある（判断カード、旧来の ASK.md、子の AskUserQuestion）
  12. 台帳のずれ（ペインの無い進行中の便）を直す者がいない
  13. 名前の衝突がある。agent_prompts が 2 つあり、見守りと見張り、hooks_dispatch と session-dispatch も紛らわしい
  14. 新規タスクの起動が引き継ぎの経路を流用していて、どの層も両者を区別できない
  15. ハーネスのコード（見張りを含む）を、アプリが同梱して配っている。調査時点では live と一致
