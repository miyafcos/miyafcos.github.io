アプリの再開は一本の経路です。data.json と ~/.mycmux/pane-sessions/ に残した会話の ID を、CLI の --resume に渡します。全ペインを一斉には起こさず、画面に出たペインから順に起こします。

起動の経路は 2 本あります。claude、codex、grok は CLI を直接起動します。claude-codex と手動の再開（Ctrl+P、続きから、Ctrl+Shift+T、spawn --resume-session）は、ランチャーを通ります。

model と effort はどこにも保存されず、再開すると CLI の既定に戻ります。ハーネスの resume-inject は、会話の再開ではありません。「全体で最新の別のセッション」の要約を SessionStart のたびに足す仕組みで、ペインを区別しません。

このページでは、セッションが途切れても続きから始めるための仕組みを、アプリ側とハーネス側に分けて説明します。「resume」という語は、コードと運用で 13 通りの意味に使われています（ページ末の表）。

安全弁を足しながら、作り直してきた経緯があります。始まりは 5 月の版の事故で、Ctrl+P の環境変数が他のペインへ漏れ、勝手に resume されました。その後、7 月の遅延 resume と、8 月下旬の「再起動で別の会話が戻る」事故の修正が続きました。

このページの目的は、いまの再開の経路と、アプリとハーネスがそれぞれ何を覚えているかを 1 枚に並べることです。

何を覚えているか

項目アプリハーネス食い違いの余地
ペインと会話の対応data.json（タブとペインの 2 か所）・pane-sessions（4 系統が書く）委譲の台帳の claude_session_id 列・復旧マニフェスト（8 月末で停止）同じ対応が 4 か所にある。正は data.json と pane-sessions
model と effort保存しない（起動時の一時環境変数）復旧マニフェスト（停止中）と設定の既定再開すると既定に戻る
会話そのもの持たない（CLI の記録を参照）~/.claude/projects・~/.codex/sessions・~/.grok/sessionsアプリの再開は、ハーネスの保持設定（Claude は cleanupPeriodDays = 999999）に頼っている
会話の一覧Ctrl+P の索引（17,886 件、人の発話なしを隠す）session-archive の index と live（2,131 件）索引が 2 つあり、選び方が違う
前回の続きの要約セーブポイントの handoff.md・Ctrl+P の引き継ぎ書（明示、セッション単位）resume-inject と session-inject の注入（暗黙、全体で最新）resume したペインに、別の会話の要約が入る

起動時の復元

  1. data.json を読む
  2. 対応表で穴埋め
  3. 重複を除く
  4. レイアウトを戻す
  5. 画面に出たペインから起こす
  1. リーダー窓が data.json を読み、全ペインの ID で ~/.mycmux/pane-sessions/<ペインの ID>.txt を読む（src/components/layout/SocketListener.tsx:1758-1773）
  2. 空のタブを落とし、対応表で空欄を埋め、同じ会話を 2 つのペインが持っていれば 1 つだけ残す（dedupeAgentSessionsInConfigs）。負けたペインの ID は消して、記録だけ残す
  3. 切り離していたワークスペースは、窓として開き直す
  4. 自動保存を最大 30 秒止めてから、レイアウトを戻す。保存した PTY の ID をそのまま使う
  5. 実際の起動は、画面に出たとき。同時にマウントするワークスペースは 1 つ、各タブでマウントするのはアクティブなペインだけ。これは 7 月下旬の事故の再発防止で、全ワークスペースを一斉に戻して Claude が 15 本（1 本約 610MB）立った（tests/test_session_restore_race.py:45-60）

Rust の create_session は、保存した ID の記録（transcript）が実在するかを確かめます（src-tauri/src/commands/terminal/agent_restore.rs:246-301）。無ければ、Claude で ID の形が正しいときは、同じ ID で新しく始めます。それ以外は、画面に「以前の会話を戻せなかったので新しく始める」と出して、新規で起動します。8 月下旬以降、--continue のような「同じフォルダの別の会話を掴む」降格はしません。

種類ごとの再開コマンド

種類再起動後の経路コマンド

codex直接起動codex resume --no-alt-screen [-C <cwd>] <ID>
grok直接起動grok --no-alt-screen --resume <ID>
claude-codexランチャー経由claude-codex --resume <ID>（記録の実在は確かめない）
agy・hermes・ompなし会話の ID を追わないので、再起動すると起動メニューに戻る（推論）
shellなしシェルと cwd と scrollback だけ戻る
種類保存再起動Ctrl+P、続きから休眠複製引き継ぎセーブポイント
claude ○ ○ ○ ○ ○ ○ ○
codex ○ ○ ○ ○ ○ ○ ○
claude-codex ○ ○ ○ × ○ ○ △
grok ○ ○ × × × × ×
agy・hermes・omp × × × × × × ×

直接起動の経路（再起動後の claude）は、保存した cwd のまま claude --resume を起動します。記録がある cwd へは移動しません（移動するのはランチャー経由だけ）。記録の検証は、「どのフォルダにあっても真」です。そのため cwd がずれたペインでは、検証が通るのに、CLI が会話を見つけられない可能性があります（推論、未検証）。

model と effort が戻らない理由

  • 起動時の選択は MYCMUX_LAUNCH_MODEL、MYCMUX_LAUNCH_EFFORT という一時環境変数で、保存のときに消える（SocketListener.tsx:1088-1089）
  • 直接起動の claude は、引数に --effort を持たない
  • CLI の spawn は、resume、引き継ぎ、プロンプト付きのとき、model と effort を送らない（scripts/mycmux_agent_cli.py:471-475）
  • ランチャーの codex と grok の resume は、起動の指定を付けない

結果として Claude は、~/.claude/settings.json の effortLevel（いまは high）に戻ります。開発の記録には「medium に落ちる」とありますが、これは 8 月下旬当時の既定での観察です。いまは、max や xhigh で動かしていたペインが high に下がる形と考えられます（推測）。model と effort を覚えていたのはハーネスの session_manifest.py だけで、8 月末から止まっています。

休眠

休眠は、見えていない Claude と Codex のペインを 60 分放置で落とし、メモリを返す仕組みです（src/lib/agentDormancy.ts、src/hooks/useAgentDormancy.ts）。10 分ごとに、注意の印、通知、作業中の表示、使用量の上限が無いことを 4 回確かめてから、PTY を止めます。会話の ID は残すので、ペインを開くと、再起動と同じ経路で再開します。止めた記録を残さないため、実際に何回止めたかは分かりません。

引き継ぎやプロンプト付きで立てたペイン（委譲の子もこれ）は、ストア上のペインに MYCMUX_HANDOFF が残り続けます。起動の組み立ては、「会話の ID があり、HANDOFF が無いとき」だけ resume の変数を足します。そのため休眠で止めた後に開くと、会話の再開ではなく、指示書の読み直しから新しいセッションが始まる可能性があります（推論、未検証）。再起動後は保存時に消えるので、正しく再開します。

手動の再開

入口動き
Ctrl+P（Resume パレット）過去の Claude、Codex、claude-codex の会話を選んで右に開く。種類が違えば、引き継ぎ書（~/.crsm/handoff/）を作って新しいセッションに読ませる。grok は対象外
ランチャーの「続きから」Ctrl+P と同じ索引の直近数件
Ctrl+Shift+T閉じたペインを 10 件までメモリに持ち、開き直す。再起動すると消える
セッションの複製記録を新しい ID でコピーして、右に開く
spawn --resume-session（ハーネス）socket の spawn の resume モード
セーブポイント要約から新しいセッション、または記録ごと fork（claude --resume <新> --fork-session、codex fork）

Ctrl+P と「続きから」は、人の発話がない会話を隠します（索引 17,886 件中 13,198 件）。「Handoff from previous session.」で始まる発話は、人の入力に数えません。そのため、spec だけを渡された委譲の子は、人が一度も打ち込んでいなければ、どちらにも出ません。

これは、session-dispatch skill の SKILL.md にある「resume パレットから復帰できる」と食い違います。どの入口も、同じ会話を開いているペインが既にあるかを確かめずに、もう 1 つ開きます。

ペインと会話の対応表 pane-sessions

~/.mycmux/pane-sessions/<ペインの ID>.txt は、1 行 <種類>:<ID> の対応表で、約 2,600 件あります。書き手は 4 系統です。

  1. Rust の create_session（正しい resume の変数で起動したとき）
  2. ランチャー（resume、引き継ぎ、新規）。Claude の新規は、ペインの ID を会話の ID に使う。Codex は記録ファイルを最大 120 秒見張り、「持ち主のいないものが 1 つ」のときだけ書く
  3. PTY モニタ（前景のプロセスの引数と、記録ファイルから帰属を決める）
  4. hook（申告を受けたとき。hook で決まった値は、同じ起動中はモニタの上書きより優先）

30 日を過ぎて誰も参照していないものは、起動時に ~/.mycmux/sessions-trash/<年月>/ へ移ります。trash を消す仕組みはありません。

ハーネス側の仕組み

スクリプトいつ何をするか状態
~/.claude/scripts/resume-inject.py SessionStart（起動、resume、clear、compact のすべて）全体で最新の「完了していない別のセッション」の要約を、<resume-context> で注入する稼働（調査当日 49 件）
session-inject.py最初の UserPromptSubmit直近のセッションの要約を注入する稼働
checkpoint.pyファイルを書いたあと（60 秒ごと）~/.claude/session-archive/live/<ID>.json を書く稼働
session-summarize.py Stop要約の md と index を書く稼働
session_manifest.py・session_guard.py定期（止まっている）全ペインの会話 ID と model、effort を記録し、復旧コマンドを作る休止（8 月末から）

resume-inject は、見出しに「Stop 未発火の前回セッション」とありますが、実際には選別が働いていません。live のファイルを書く checkpoint.py は、完了の印を常に false で書きます。Stop 側は live を更新しません（live の 2,131 件はすべて未完了）。

実際に選ばれるのは「最近ファイルを書いた別のセッション」で、ペイン、cwd、案件を区別しません。調査当日の 49 件の注入で、同じ 1 件が 11 のセッションに入りました。

mycmux がペインを resume すると、SessionStart がもう一度発火します。そのため、再開した会話に無関係な要約が足されます。この調査をしたセッションの冒頭にも、別の案件の要約が入っていました。

既知の事故と対策

  • 5 月上旬 Ctrl+P の環境変数が他の PTY へ漏れ、新しいペインが勝手に resume された。対策として、会話の ID を保存しない仕様にした
  • 5 月上旬 多層の安全弁とセットで、保存を再導入
  • 7 月下旬 全ワークスペースの一斉復元で、Claude が 15 本立った。対策は遅延 resume
  • 7 月末 巡回で起きたエージェントがメモリを占有した。休眠の閾値を 120 分から 60 分へ
  • 8 月中旬 fork 起動の複製が不安定だった。記録のコピー方式へ
  • 8 月下旬 再起動で別の会話が戻った（無言の --continue 降格など）。降格を廃止し、対応表のキーをペインの ID に
  • 9 月上旬 引き継ぎで立てたペインからの spawn で、子が親の指示書を再演した。ランチャーが変数を読んだ直後に消すように
  • 未解決 resume 後に effort が既定に戻る（運用で /model を戻している）

「resume」が指す 13 のもの

#呼び名実体
1 CLI の resume claude --resume・codex resume・grok --resume・claude-codex --resume
2アプリの自動再開data.json から、画面に出たペインを順に起こす
3休眠からの復帰止めたペインを開くと、2 と同じ流れ
4 Resume パレットCtrl+P
5続きからランチャーの直近数件
6閉じたペインの復活Ctrl+Shift+T
7 --resume-session socket の spawn の resume モード
8セッションの複製記録をコピーして、新しい ID で resume
9引き継ぎ（handoff）引き継ぎ書や指示書を読ませる新しいセッション
10セーブポイントの参加要約なら引き継ぎ、記録ごとなら fork
11 resume-inject別のセッションの要約を注入する（会話は再開しない）
12 Resume Command要約の md に書く claude --resume <ID> の 1 行
13識別子の名前MYCMUX_RESUME・resumeSessionId など

「引き継ぎ（handoff）」も、5 通りに使われています。

  • Ctrl+P の引き継ぎ書（~/.crsm/handoff/）
  • セーブポイントの handoff.md
  • Web ペインの引き継ぎ書（~/.mycmux/handoff/）
  • 親の手書きメモ（~/.claude/dispatch/session-handoffs/）
  • プロンプト付きの spawn。委譲の spec を配るだけでも、MYCMUX_HANDOFF と「Handoff from previous session」の文面を使う

「session id」も、6 種類あります。

  • PTY の ID（MYCMUX_PANE_SESSION_ID、socket の --session）
  • ペインの ID（対応表と scrollback のキー）
  • エージェントの会話の ID（--resume-session）
  • 旧名の claude_session_id
  • Ctrl+P の索引の ID
  • セーブポイントの ID

境界の食い違い

  1. model と effort の記憶が、どこにもない（アプリは捨て、ハーネスの記録は止まっている）
  2. 「前回の続き」の注入が 2 系統あり、互いを知らない。resume したペインに、無関係な要約が入る。Codex の hook は起動時だけなので、この上乗せは Claude だけに起きる
  3. 会話の索引が 2 つ（Ctrl+P と、ハーネスの session-archive）あり、別々の基準で「前回」を決めている
  4. ハーネスの文書（子は resume パレットから戻せる）と、アプリの挙動が食い違う
  5. ペインと会話の対応の書き手が、アプリの中だけで 4 系統、ハーネスにも 2 つある
  6. ~/.claude.json の信頼を、Rust とランチャーの 2 か所が書く
  7. アプリの再開は、ハーネスの記録の保持設定に頼っているのに、その前提の記述も検査も無い
  8. 同じ会話を 2 か所で開ける（後から、保存時の重複除去と、CLI の「already in use」で止まる）
  9. 「死んだら resume で立て直す」は、どちらにも実装がない（ハーネスの session_guard は関数だけ残り、呼ばれていない）
  10. 引き継ぎの変数を一度きりにする責任が、ランチャー（橋）とストア（アプリ）に分かれている
  11. 起動の引数と resume の変数の組み立てが、アプリの中で 3 か所に分かれている（TerminalPane.tsx、DetachedPaneShell.tsx、socketCommands.ts）
  12. 使われない保存物がある。history.db、重複除去の記録、MYCMUX_RESUME_FORK、セーブポイントの自動記録の理由、Python のセーブポイント CLI、ランチャーの ID なしの分岐
  13. 文書が古い（README の「crsm を別にビルド」、history の「PTY の ID は再起動で変わる」）
