mycmux は、複数のエージェント製品をペインで並べて動かすターミナルワークスペースです。安全な操作、状態の観測、委譲に伴う記録を、共通の制御 API で出します。エージェントの内部の実行ループや、仕事の分け方と評価の基準は持ちません。

原則は、次の一行にまとめられます。

「本体は操作と記録の整合を守り、アダプターは対応する機能と制約を申告し、skill は仕事の進め方を選び、利用者は判断の基準と許可を与える」

どの部品も、自分で確かめられない結果を「保証した」とは言いません。作者はこれを、2026-09-25 に設計の記録（ADR 0014）として決めました。

ここまでの 9 ページの調査で、mycmux が自分の外側の仕組みと両方向に依存していることが分かりました。このページでは、その結果を受けて作者が決めた立ち位置と語、5 つの領域、ルール、受け渡しの約束、移す順番を説明します。最後に、調査で見つかった既知の問題と直し方の候補 22 件を載せています。

9 月 24 日の原則を置き換えた理由

9 月 24 日の版は、原則を「アプリはペインの実行、観測、表示を受け持ち、ハーネスは仕事の流れと方針を受け持つ」としていました。ここでの「ハーネス」は、作者の ~/.claude にある skill、hook、スクリプト、台帳のことです。業界では、エージェントハーネスは Claude Code などの製品の内部で、ツールの実行、文脈、権限、実行ループを受け持つ基盤を指します。

語がずれていただけではありません。この原則は、委譲の台帳や判断カードの置き場を、Claude Code の設定の側に決めてしまっていました。Claude Code でも Codex でもほかの製品でも同じように使う、という作者の意図と合わないので、立ち位置から決め直しています。以降は、作者の設定を skill、個人の hook、スクリプト、台帳、rules といった部品の名前で呼びます。

5 つの領域

5 つは上下の層ではなく、受け持ちの区分です。

領域受け持つもの約束
エージェント製品対話、ツールの実行、権限、会話の記録mycmux は中身を変えない
エージェント別アダプター起動と再開の引数、hook の導入と共通イベントへの変換、会話 ID の取得、能力の申告。任意で、質問ツールの抑止、親への差し込み、ログインの切替固有の形式は閉じ込め、隠せない差と制約は申告する。製品と実行方式と版の組み合わせごとに持つ
mycmux 本体ワークスペース・ペイン・PTY・保存、状態の判定、起動の指定、委譲タスク・質問・回答・配送の記録、画面、制御 API製品の名前で固有の処理を分岐しない。記録と操作の整合を守る
skill仕事の進め方（委譲の手順、待ち方、やり直し、人に聞く条件、評価）公開された制御 API だけを使う
利用者・プロジェクトの設定と指示規則、モデルの割り当て、品質の基準、個人の hook、指示文書（CLAUDE.md、AGENTS.md）mycmux は中身を解釈しない。mycmux が出すのは合図（環境変数とイベント）だけ

エージェント別アダプターは、利用者向けには「エージェント連携」と呼び、設計とコードでは「アダプター」と呼びます。制御 API は、mycmux の操作と照会の約束です。socket は通り道、JSON Lines は書式、CLI は利用プログラム、MCP は出し方の 1 つです。

すみわけの決め手は、「その記録や処理は、親や skill が止まっても成り立っていなければならないか」という問いです。成り立つ必要があれば本体に置きます。製品固有の形式を扱うならアダプター、仕事の進め方の判断なら skill、個人の基準なら利用者の設定に置きます。この問いはエージェントの種類によらないので、Claude Code と Codex のどちらが親でも同じ答えになります。

依存の向きは、次の 3 つの決まりで表します。

  • skill、CLI、MCP、画面は、共通の制御サービスを使う
  • 制御サービスは、製品固有の処理をアダプターに頼む
  • 利用者の設定は、明示した入口からだけ本体に入る

「本体はエージェントの名前を知らない」とまでは言いません。画面に Claude Code と表示するのは構いませんが、起動の引数や会話記録の形式を本体のあちこちに書き込むことはしません。

本体と skill の受け持ち

オーケストレーションを本体に持つかどうかは、二択にしていません。回答を保存する、配送を試みる、届いたか分からなければそう記録する、取り消したタスクへは届けない、といった段取りは本体に要ります。これを skill に置くと、回答が届くかどうかが親の次の発言しだいになってしまうからです。調査から実装へ進める、失敗したら別のモデルでやり直す、レビューを足す、といった仕事の段取りは skill に置きます。

本体が持つものskill と利用者の方針が持つもの
タスクの登録、親子関係、担当の実行、状態の移り変わり、結果の提出の記録仕事をどう分けるか、誰に任せるか、何件並べるか
質問と回答の保存、回答者の確認、配送の状況、期限切れの扱い何を人に聞くか、どの判断を親に任せるか
宛先の確認、送信の取り違えと二重送信の防止どんな指示を足すか
状態の観測、経過時間、異常の根拠、共通の表示「この静けさは問題か」「指示し直すか」「別の子に替えるか」
提出と検収（提出された結果を親が確かめて受け取ること）の区別、履歴、片付けの仕組み品質の基準、レビューの仕方、成果を採るか

親がいなくても何段もの仕事を自動で進めたい、という要件が出てきたら、そのとき独立した実行部を足すかを決めます。いま作る必要はありません。

ルール（10 本）

  1. 本体は、エージェント製品の名前で固有の処理を分岐しない。固有の処理はアダプターに閉じ込める
  2. アダプターは、固有の形式を共通のイベント、操作、能力に変換する。隠せない差と制約は、能力として申告する
  3. skill は公開された制御 API だけを使い、本体の内部のファイルや DB を読まない。本体も、skill や利用者の設定の非公開の形式に頼らない
  4. 残る事実には、持ち主を 1 つだけ決める。ほかは写しか表示にする（状態、ペインと会話の対応、委譲タスク、質問）
  5. 委譲タスク、質問、回答、配送の記録は本体が持ち、仕事の進め方は skill が持つ
  6. 制御 API とイベントには、版と能力の照会を付ける。未対応は成功ではなく「未対応」として返し、別の意味の操作へ黙って代えない
  7. エージェントの設定と認証への書き込みは「連携の導入」として明示する。入れる、止める、外すを用意して、自分が入れた部分だけを変える
  8. 観測には情報源と確度を付ける。推定を事実に格上げせず、確かめられない結果を「保証した」と言わない
  9. 子の報告、質問、画面の文字は、信頼しない入力として扱い、親への指示に格上げしない
  10. 語は業界の用法に合わせる。「ハーネス」は、エージェント製品の内部の実行基盤を指すときにだけ使う

約束の範囲は事故の防止です。同じ OS ユーザーで動く悪意のあるプロセスからの完全な隔離はせず、各製品のサンドボックスに任せます。そのうえで、子には自分のペインと自分のタスクだけを扱えるトークンを渡し、全体を操作できるトークンは親と画面だけが使います。子からほかのペインへの送信と終了は、親か人の承認を通します。

識別子と状態

ペイン ID、実行 ID（起動ごと）、会話 ID、委譲タスク ID、質問 ID、送信の操作 ID、イベント ID を分けて持ちます。会話 ID は製品のものなので、アダプターの種類と認証プロファイルに結び付けます。分けておかないと、前にそのペインにいた子への回答が、新しく入った子へ届いてしまいます。

状態も 1 つの値に詰め込まず、軸ごとに持ちます。

  • プロセス: 起動中、稼働、終了、確認できない
  • エージェントの活動: 作業中、入力待ち、確認できない
  • 注意が要る理由: 業務上の質問、権限の承認、ログイン、その他
  • 委譲タスク: 未着手、実行中、結果提出済み、検収済み、失敗、取消

ターンの終わりはタスクの完了ではなく、出力がないことは停止の証明ではありません。「60 秒出力がない」は観測した値として出し、そこから先の判断は skill に任せます。

エージェントごとの差

差は隠さず、アダプターに申告させます。申告は「強制できる」「指示で頼むだけ」「未対応」「未確認」の 4 段階です。製品名だけでなく、実行ファイルの版、実行方式、設定での有効と無効、試験した範囲に結び付けます。強制が要る委譲で条件を満たさない製品なら、起動を断るか、人が見る運用に切り替えます。

調査時点の対応は次のとおりです。○ はできる、△ は条件つき、× はできない、? は要確認です。

製品起動と観測委譲まわり
claude起動 ○、hook の申告 ○（7 種）、起動ごとのトークン ○。会話 ID の保存 ○、再起動後の再開 ○、model と effort の保持 ×手動の再開 ○、引き継ぎ ○、アカウント切替 ○。子の質問ツールの抑止と親への差し込みは ○（個人の hook）。skill の配布 ○（スキルパック）
codex起動 ○、hook の申告 ○（4 種）、起動ごとのトークン ○。会話 ID の保存 ○、再起動後の再開 ○、model と effort の保持 ×手動の再開 ○、引き継ぎ ○、アカウント切替 ○。子の質問ツールの抑止 ?（内蔵の request_user_input がある）。親への差し込み ?（公式には仕組みがある）。skill の配布 △（プラグイン）

差が出る機能は、主に次の 4 つです。

  • 子の質問ツールの抑止: 特定の質問ツールを止めることと、子が人への質問で止まらないことは別物です。指示文で使わないよう頼んでも、強制にはなりません。Codex にも内蔵の request_user_input があり、止め方は未確認です
  • 親の会話への差し込み: Claude Code にも Codex にも、UserPromptSubmit で文脈を足す仕組みがあります。どちらも親の次の発言に付くもので、親を起こす保証ではありません。共通の約束は「質問は画面と API から必ず見える」までとし、差し込みは任意の知らせにします
  • 再開: 求めた値と適用できた値を分けて記録し、確かめられない値を「戻した」と表示しません。同じ high を渡しても、製品が違えば同じ推論量とは限りません
  • ログインの切替: 起動の引数とは分けた、権限の強い任意の機能にします。認証情報の置き場は製品ごとに違うので、認証ファイルを書き換える方式を共通にはしません

規格の使い分け

hook は出来事を受け取る手段で、完全な強制の境界ではありません。Agent Skills は手順の配布の形式で、永続のキューや権限の代わりにはしません。MCP は制御 API の出し方の 1 つで、別の台帳や判定を作りません。指示文書は、拡張の仕組みと同列には扱いません。

ACP と Codex App Server は、1.x で試験します。Codex の会話記録は、公式が「安定したインターフェースではない」としているので、正本にはしません。

受け渡しの約束（16 本）

約束は、実行時の操作 9 本、導入と設定 4 本、全体の規則 3 本の、あわせて 16 本です。各約束には、入力と対象、呼び出し元の責務、成り立つ条件、保証する結果を書きます。あわせて、失敗や結果不明のときの扱い、同じ要求を再送したときの扱い、製品ごとの差、保証しないことも書きます。

作り方の説明（「Enter は 1 回」など）ではなく、外から確かめられる文で書くのが決まりです。下の表は、そのうち保証することと保証しないことだけを抜き出したものです。

実行時の操作（9 本）

約束保証すること
1 起動起動の指定（製品、model、effort、起動の種別、サンドボックスなど）を起動前に確かめ、必須の指定を適用できなければ起動しない。同じ要求の再送で実行を増やさず、求めた値と適用できた値を返す。エージェントのログインや指示の受理は保証しない
2 状態の知らせ登録済みの実行に結び付く申告だけを受け付け、イベント ID で重複を見分ける。終わった実行の申告を、今の実行に当てない。申告の中身の正しさは保証しない
3 状態の読み取り同じ改訂番号に対し、画面と API は同じ判定を使う。不明、未対応、対象なしを、ふつうの値と取り違えない形で返す。画面と API が同じ瞬間に同じ値を返すことは保証しない
4 送信指定の実行と期待値を最新の状態と照らし、食い違えば本文も Enter も書かない。同じ操作 ID で二重に提出せず、結果を確かめられなければ「不明」と返して自動で送り直さない。入力が目的どおり実行されたことは保証しない
5 委譲タスク登録、親子関係、担当の実行、状態の移り変わり、やり直しの試行を本体が記録し、制御 API から読めるようにする。仕事の分け方と任せる先の妥当さは skill の判断で、保証しない
6 人への質問受け付けたと返す前に記録し、画面と API から見えるようにする。有効な回答を 1 つに確定し、回答の保存、配送、配送の確認、解決を別々に記録する。親への差し込みは任意の知らせで、親が読んだことは保証しない
7 結果の提出と検収提出をタスクと試行に結び付けて保存し、成果物は参照で登録する。提出済みと検収済みを分ける。成果の正しさは保証しない
8 再開同じ会話の再開と引き継ぎを別の操作にする。確かめられない値を「戻した」と表示せず、再開できないときに新しい会話で黙って代えない。製品が違っても同じ推論量になることは保証しない
9 中断、取消、終了ターンの中断、仕事の取消、プロセスの終了、ペインの削除、会話や成果物の削除を別の操作にする。外に出た副作用の巻き戻しは保証しない

導入と設定（4 本）

約束保証すること
10 環境変数実行ごとに、その実行用の環境を渡す。一度きりの起動指示を永続の設定へ残さず、ほかの実行に使い回さない。起動の種別を知らせる。子プロセスがさらに起動したプロセスへ変数が渡らないことは保証しない
11 連携の導入製品ごとに、入れる、止める、外す、状態を見るを用意する。自分が入れた部分だけを変え、重複させず、利用者が足した設定を消さない。製品の設定の形式が変わったあとも働くことは保証しない
12 skill の配布原本 1 つを配り、製品ごとの置き場と要るものを管理する。入れた先と版を記録し、利用者の変更を黙って上書きしない。保証するのは、対応を宣言した製品と版の組み合わせだけ
13 認証プロファイルの切替本体は秘密を持たず、認証プロファイルへの参照だけを持つ。公式の切替と設定フォルダの分離を先に使う。製品の非公開の保存形式が変わっても切り替えられることは保証しない

全体の規則（3 本）

約束保証すること
14 版と互換API の版、通信仕様の範囲、操作と能力の一覧を照会できる。互換は要求、応答、イベントの仕様で判定する。受け手は知らない項目を無視し、知らない状態の値を「不明」として扱う。保存データの形式の巻き戻しは、通信の版とは別に管理するので保証しない
15 操作の権限子には自分のペインと自分のタスクだけを扱えるトークンを渡し、全体を操作できるトークンは親と画面だけが使う。子からほかのペインへの送信と終了は、親か人の承認を通す。同じ OS ユーザーで動く悪意のあるプロセスからの完全な隔離は保証しない
16 保存、復旧、再配送成功を返す前に何を保存するかを決める。再起動のあとの未完了の処理、再送、届いたか分からない配送、購読の取りこぼし、保存期間も決める。アプリが落ちた瞬間の入力の配送は保証しない

いまの機能の行き先

調査で確かめた現状を、5 つの領域に当てはめました。括弧の中の段は、下の「移す順番」の段です。

いまの機能いまの置き場と困りごと行き先
委譲の台帳Claude Code の設定フォルダの下のファイルに、skill のスクリプトが書く。アプリの委譲の見守りが、古い規則で直接読む。進行中の 45 件のうち 29 件はペインがない本体（制御 API で読み書き）。新しいタスクから切り替え、二重書きはしない（段 3）
判断カードのキュー個人の運用フォルダにあり、アプリの画面のカードとつながらない本体の「質問」として記録し、画面に出す（段 3）
親への差し込みClaude Code の UserPromptSubmit の hook。Claude Code の親にしか届かないアダプターの任意の機能。Codex にも同じ種類の hook がある（段 4）

見張り（9 月中旬から停止中）個人の常駐スクリプト。止まった子の検知が 4 系統ある材料（60 秒の静けさなど）は本体、判断は skill。通知、再送、終了をする側は 1 つだけにする（段 2〜5）
model と effortどこにも保存しない。再開すると、黙って既定に戻る本体の起動の指定。求めた値と適用できた値を分けて持つ（段 1）
hook の導入アプリが起動のたびに 3 製品の設定へ書く。止める画面がなく、Grok には 5 重に入るアダプターの「連携の導入」。入れる、止める、外す、状態を見るを用意する（段 1）
前回の要約の差し込み（resume-inject）個人の hook。mycmux が再開したペインにも、無関係な要約を入れる利用者の設定のまま。本体が起動の種別（新規、ネイティブの再開、引き継ぎ）を知らせる（段 1）
skill の配布Claude Code 用はスキルパック、Codex 用は別のスクリプトがプラグインを作る。二重管理になっている原本 1 つと、製品ごとの導入処理。Codex の置き場は要確認（段 4）
制御 API の版版を問うコマンドがない。skill が作業ツリーの CLI を使い、稼働中の exe と版がずれる版と能力の照会を足す。MCP も同じ処理を呼ぶ（段 1）
アカウント切替アプリが各製品の認証ファイルを書き換える。製品の非公開の形式に頼っている任意の機能として分ける。公式の切替と設定フォルダの分離を先に使い、本体は認証プロファイルへの参照だけを持つ（段 5）
エージェントの家未実装のまま凍結中1.x で、本体の委譲タスク、質問、結果の記録の上に skill として建てる方向。新しい DB は作らない（まだ決めていない論点）
使用量、AI ログ、自動命名、Jev の再配置アプリ本体のまま（周辺の機能）

移す順番

作り直しではなく、いまの Claude Code の運用を生かしたまま段階的に移します。先に直すのは、語や配布の形式ではありません。送信の安全、タスクと質問の持ち主、未対応と結果不明の表し方です。

段すること
0 いまを固定する（1.0）いまの版、hook の設定、台帳、起動と質問と再開の実例を控える。Codex が skill をどこから読むかを、試験用の skill で確かめる
1 危険な食い違いを直す（1.0）版と能力の照会を足す（既知の問題 3）。model と effort の黙った脱落（4）、経路ごとの Enter の回数、期待値なしの回答（6）を直す。hook の重複を止めて、導入の状態と入切を見せる（2）。CLI の全件取得の失敗（1）、起動の種別の合図（9）、Codex の Stop hook（22）も直す
2 状態と入口を 1 本にする（1.0）画面と API の判定を共通にする（12）。いまの台帳を読む仮のアダプターを置き、アプリと skill に散らばった直接の読み取りを減らす。見張りの起動の試みを外す（7）
3 タスクと質問の正本を本体へ（1.x）本体のサービスだけが更新する保存領域を作り、質問を画面に統合する。回答と配送は別に記録する。子に渡す限定のトークンもここで入れ、新しいタスクから新しい方式に切り替える
4 skill を 1 本の原本に（1.x）3 つの skill の原本を 1 つにし、Claude Code と Codex の両方から同じ API を使う。いまの hook は、配送のアダプターとして残す（18）
5 出し方を増やし、古い経路を外す（1.x）必要な操作から MCP で出す。ACP と Codex App Server を試験し、アカウント切替を公式の方法へ寄せる。旧台帳の読み取り、重複した見張り、要らなくなったラッパーを外す（19、21）

段 1 は既知の問題の修理ですが、版と能力を問い合わせるコマンドと、hook の入切を見せる画面という小さな追加を含みます。この 2 つは、1.0 計画の「新しい機能は止める」の例外として認めました（決めたこと 3）。段 3 からは、委譲タスクと質問という新しい仕組みにあたるので、1.x で扱います。

段 3 では、同じタスクを旧台帳と新しい記録の両方が更新する期間を作りません。二重書きの期間は、どちらが正しいか分からない記録を生むからです。比べながら動かす期間も、通知、再送、終了をする側は 1 つだけにします。

決めたこと（7 件）

設計案で「決めること」として挙げた 7 件は、2026-09-24 の夜から 25 日の未明にかけて、作者が裁定しました。1、2、3、5、6 は推奨どおりです。4 は推奨と違う選択で、7 は選び直しの途中で足した中間の案です。

論点作者の裁定
1 委譲タスクと質問の記録を、本体が持つか本体が持ち、制御 API から読み書きする。~/.mycmux の中立のファイルに置いて skill が直接読み書きする案と、いまのまま ~/.claude の下に置く案は採らなかった
2 語の扱い（「ハーネス」）エージェント製品の内部の実行基盤にだけ使い、作者の設定は部品の名前で呼ぶ。語を残して意味を定義する案は、Claude Code の設定の側に寄せる読み方が残るので採らなかった
3 どの段から着手するか段 0 と 1 から始め、段 2 までを 1.0 のうちに行う。段 1 の版の照会のコマンドと hook の入切の画面は、1.0 計画の例外として認める。段 3 以降は 1.x
4 構造化された接続（ACP と Codex App Server）1.x で試験する。推奨は「今は採らず、境界だけ残す」だった。段 5 の試験と、要確認の 7 が 1.x の作業に入る
5 アカウント切替任意の機能として残し、公式の切替と設定フォルダの分離へ寄せる。本体は認証プロファイルへの参照だけを持つ
6 開発者向けページの公開の時期語と原則を直してから、一度に公開する
7 約束がどこまでを守るか事故の防止を範囲とし、完全な隔離は各製品のサンドボックスに任せる。子には自分の範囲だけの権限を渡し、ほかのペインへの送信と終了は親か人の承認を通す。危ない委譲は、起動の指定で製品のサンドボックスを選べる

画面を読んで Enter を送るいまの経路では、「入力が受理された」を厳密には確かめられません。4 の裁定で、それを確かめられる道を 1.x で試すことになりました。

7 は最初、「事故を防ぐ範囲に限る」と「悪意のある子からも守る」の 2 案で聞いていました。後者は mycmux だけでは守れず（子は利用者と同じ権限で動く）、Windows 11 Home では実行環境を分ける手段が限られます。さらに、G: ドライブや Office や Chrome を使う委譲が回らなくなります。一方で前者には、乗っ取られた子が mycmux の CLI でほかのペインや親へ届く弱さがあり、これを比べ直して中間の案を足しました。

エージェントの家

書くだけで読まれないデータ

  • 論点: 対象は 3 つです。history.db（2.88GB、読む側なし）、個人の hook のターンと通知の記録（agent-turn-events.jsonl、agent-notifications.jsonl、読む側なし）、hook 台帳の古い行です。hook 台帳そのものは、受付の検査が同じ出来事の重複を見分けるために読んでいるので（src-tauri/src/agent_state/ledger.rs:131）、止められません。ただし、古い行を読む処理はなく、削除もされません（約 9.4 万行）
  • 選択肢:
    • ア 読む側のないものは書くのをやめ、hook 台帳には保持期限（たとえば 30 日）を付ける（推奨）
    • イ 読む側を作る（history の検索を AI に使わせるなど）
  • なぜ論点になるか: ディスクと処理時間を使い続けていますが、history.db と上の 2 つの記録は、どの機能も読みません。hook 台帳も、古い行は使われていません。止めるか使うかは、機能の方針です
  • いま困っていること: history.db は、40 日で 2.88GB になりました。hook 台帳の置き場は、ほかの機能の DB（workorders.db）を 195MB まで太らせています
  • 選んだときに起きること: アなら、小さな改修で止まる。hook 台帳は直近の行が残るので、受付の検査の照合は変わらない。後で読む側が欲しくなったら、取り直しになる。イなら、読む側を作る設計が要る
