ペインの状態（動いている、人を待っている、終わった）を実際に決めているのは、Rust の session_state です。hook、画面スキャン、PTY モニタ、Codex の記録の 4 つの入口がここに合流し、画面の各所に配られます。設計文書（ADR 0010）で「唯一の合流点」とされた agent_state の reconciler は、hook の入口の関所と台帳に縮んでいます。

Rust の気づきカード（attention_cards）は仕組み上ほぼ空で、全期間で 1 行でした。ダッシュボードの「気づき」列にいま出ているのは、画面側が毎回組み立てる事実カードです。ハーネスの判断カードは、アプリのカードとはつながっていない別の系統です。

このページでは、エージェント（Claude、Codex、Grok）の様子を観測してから、人に知らせ、人が処置するまでの流れを説明します。8 月末の作戦（docs/plans/2026-08-31-observation-contract-roadmap.md）は、この流れを 4 つの層に分けました。「観測 → 判断 → 提示 → 処置」です。主軸は、観測の決まり（観測契約）を 1 本にまとめることでした。

その後、提示の面は大きく入れ替わっています。ベルは 9 月上旬に削除、報告インボックスは 9 月中旬に撤去、要対応の帯は master に入らないまま破棄されました。

このページの目的は、いまどの入口と判定が生きていて、どの画面が何を読んでいるかを示すことです。あわせて、「カード」と「判断」という語が指す別々のものを見分けられるようにします。

状態を決める場所 session_state

session_state は、ペインごとの状態を 1 つにまとめる Rust のモジュールです（src-tauri/src/session_state/mod.rs）。まとめるのは、「生きているか・動いているか・人を待っているか（attention）・観測が健全か」です。4 つの入口の証拠はすべてここに入り、変化があると status feed（状態の配信口）から、画面とソケットの購読者へ配られます。

attention（人に気づいてほしい印）の合成の決まりは、次のとおりです。

  1. 古い世代の証拠は捨て、新しい世代の証拠が来たら状態を初期化する
  2. hook の「なし」は、すべての入口の attention を消す。他の入口の「なし」は、自分の分だけを外す
  3. 同じ種類で同じ id なら、入口を足して 1 つにまとめる。完了（done）同士は、id が違っても同じものとして扱う
  4. それ以外は、観測時刻が新しい方で丸ごと置き換える

同じペインの状態が、見る場所によって食い違います。60 秒黙ったら「待機」とみなす判定は、socket の session.state_view にだけあります。アプリの画面が読む status feed にはありません（src-tauri/src/session_state/mod.rs:273-318 と src-tauri/src/status_feed.rs:31-46）。

ハーネス、bridge、pocket は前者を、アプリの画面は後者を読みます。実測では、生きている 24 ペインのうち 4 ペインで、両者が食い違っていました。

ほかに、書かれるだけで使われない値があります。証拠の有効期限（stale_after）は運ばれるだけで、失効の判定がありません。「エラー」の attention を作る入口もないため、画面の「エラー」は実質的に使用量上限でしか点きません。閉じたペインの記録も、消されずに残り続けます（測定時 114 件のうち 90 件が終了済み）。

hook の経路

hook は、エージェント自身が「質問を出した」「ターンを終えた」などを知らせる仕組みです。アプリは起動のたびに、ハーネスの設定ファイル（~/.claude/settings.json、~/.codex/hooks.json、~/.grok/config.toml）へ自分の hook を書き込みます（src-tauri/src/agent_state/settings.rs:89-169）。

  1. ペインで起動
  2. 合言葉の発行
  3. helper が申告
  4. 関所で照合
  5. 状態に反映
  1. ペインで claude などを打つと、ランチャーの関数が socket の launch.issue_hook_cap を呼ぶ。使い捨ての合言葉（capability、32 バイトの乱数）を受け取り、子プロセスにだけ環境変数 MYCMUX_HOOK_CAP で渡す（src-tauri/src/launcher.sh:88-128）
  2. エージェントのイベントのたびに、helper ~/.mycmux/hooks/v1/mycmux_hook.py が起動する。合言葉が無ければ何もしない。0.5 秒で打ち切り、失敗しても常に正常終了する
  3. helper は、socket の hook 専用の口（hook realm）へ申告する。一般の合言葉（token）と hook の合言葉の両方を持つ要求は拒否される（src-tauri/src/socket.rs:180-208）
  4. 関所（agent_state の Reconciler と台帳）が、起動の世代、重複、レート制限を照合して受け付ける
  5. 受理された申告を、session_state の attention に写す
hook の申告session_state の attention
attention_required（質問・承認・通知）入力待ち
turn_ended（ターン終了）完了
turn_active・process_exited・session_terminated・cancelledなし（すべての入口の分を消す）
failed・rate_limited写さない

台帳 agent_state_ledger は 93,781 行で、その 92% は Claude の turn_active（ツールを使う前の申告）です。Claude の申告にはターンの ID が無いので、イベント 1 つが 1 ターンとして記録されます。

台帳を消す処理が無く、置き場の ~/.mycmux/workorders.db は 194.7MB まで増えています（調査当日の夕方の測定）。書き込みが続いているので、ページによって 192〜195MB、93,781〜94,115 行と、測った時刻の値が違います。台帳の受信時刻はアプリ起動からの経過ミリ秒なので、「気づく速さ」を後から測る材料になりません。

設計どおりに動いていない reconciler

ADR 0010（docs/adr/0010-agent-state-canonical-reconciler.md）は、agent_state の Reconciler を合流点に決めました。hook、rollout、プロセス、タイトルを 1 つの正しい状態にまとめ、カード作成、未読、OS 通知を「ちょうど 1 回」行う役です。実際には、次のようになっています。

ADR の決め実際
入力は hook・rollout・プロセス・タイトル本番の入力は hook だけ。Codex の rollout は Reconciler を通らず、session_state へ直接入る
rollout と hook の食い違いを 3 秒待って裁く本番では到達しない（テストでしか通らない）
カード作成・未読・OS 通知を 1 回だけ行う予約の列（card_created_at など）は書かれるが、実行するコードが無い。「OS 通知を出した」列が 6,996 行立っているのに、OS 通知を出すコード自体が無い
生きている用途古い世代の hook の拒否、質問への二重回答の防止（agent_prompt_try_answer）、起動の世代の照合

Rust の気づきカードと、画面側の事実カード

Rust の気づきカード（attention_cards、ADR 0011 の並び順）は、観測を「人が見るべきカード」に昇格させる仕組みです。ところが、昇格の条件に「WorkOrder に属するか、追跡中のペインであること」が入っています（src-tauri/src/attention/rules.rs:60-72）。追跡を登録する画面は無く（追跡 0 件）、WorkOrder も封印済みが 0 件です。そのため全期間で 1 行しか作られておらず、その 1 行も 9 月中旬に解消済みでした。

9 月中旬から、ダッシュボードの「気づき」列を埋めているのは、画面側が毎回組み立てる事実カードです（src/components/dashboard/attentionModel.ts:67-119）。1 ペインにつき 1 枚で、「質問が出ている」「入力が送られずに残っている」「30 分出力が無い」のどれか 1 つを示します。事実だけを示し、どうするかは書きません（9 月中旬の裁定）。押せるのは「このセッションを開く」だけです。

設定の「先回りカード（気づき）」をオフにして止まるのは、Rust の気づきカードだけです。気づき列に実際に出ている事実カードは止まりません（src/components/settings/tabs/AutomationTab.tsx:85-94）。

取り違えやすい点が 3 つあります。

  • reconciler は 2 つあり（agent_state と session_state）、画面に効くのは後者です
  • 「判断待ち」（委譲の ASK.md）、つまみの「入力待ち」（attention）、ハーネスの「判断カード」は、別々の出来事です。互いに連動しません
  • 「判定」は、AI の判定（次の一手、Jev、ペイン整理）にも、決まりによる判定にも使われています

境界の食い違い

どちらに寄せるかの提案は、責務の分け方にまとめています。

ハーネスとアプリの間

  1. アプリが起動のたびに、ハーネスの設定ファイルへ hook を書き込む。同じファイルに、ハーネス自身の hook が同居している。Claude Code の書き戻しで所有の印が消えた事故がある（6b49f3db で直した）
  2. アプリのランチャーが、エージェントを起動するたびにハーネスの見張りを起こそうとする（src-tauri/src/launcher.sh:130-142）
  3. Claude の質問画面の読み取りが 2 本ある（アプリの askQuestionScan と bridge）。preview 対応は bridge だけ
  4. 状態の判定が、面で食い違う（state_view と status feed）
  5. CLI の厳しい検査と、アプリの null がぶつかる。mycmux_agent_cli.py status（全件）は、閉じたペインが 1 つでも残っていると必ず失敗する（scripts/mycmux_agent_cli.py:885 と src-tauri/src/socket.rs:789-791）。pocket にも同じ検査が移植されている
  6. カードが 2 系統ある（ハーネスの判断カードと、アプリの気づきカードと質問カード）。片方で答えても、もう片方は知らない
  7. session-board は、生産者（外部ツール）と取り込みの約束が別の場所にある。生産者が止まると、取り込みも黙って止まった
  8. ~/.mycmux/pane-sessions/ を書く者が 4 系統ある（Rust の起動処理、ランチャー、PTY モニタ、hook）。resume の材料にも効く（resume）

アプリの中

  1. reconciler が 2 つある。ADR 0010 の「合流点」は session_state 側で実現した
  2. 副作用（通知数、通知音、トースト、事実カード、停滞検知）の持ち主が ADR と逆で、画面側にある
  3. 旧来の通知数と canonical の attention が並走し、つまみの点は両方を読む
  4. 並び順の決まりが 3 つある（Rust カード、事実カード、一覧）
  5. 同じ質問に、入口ごとに別の id が付く（hook と画面）。重複の裁定（fingerprint）は未着手
  6. 承認と入力待ちが、入口によって入れ替わる（画面は承認、hook は入力待ち）
