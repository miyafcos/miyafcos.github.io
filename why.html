mycmux ガイド

考え方

エージェントとの会話が増えると、全部を開いて読む時間が足りなくなります。任せた仕事が見えない場所で止まっていれば、返事が必要なことにも気づけません。mycmux は、作業を並べる場所と、状態を確かめる手段をひとつの画面に置きます。

1. 見える場所での委譲

別のエージェントへ任せた仕事も、途中で開いて確かめられる形にします。端末の区画をタブ、その中で切り替える単位をペインと呼びます。委譲先を画面上のペインとして起動したものが可視ペインです。

エージェントは Web ペインを裏で開き、読んだり操作したりできます。できる操作は別のエージェントへ任せたいに挙げています。

先に全体の構成を置きます。この節と 4 節で扱うのは、図の中で委譲 CLI と hook がローカルソケットを通る経路です。

この形にしたのは、見えない委譲で失敗したからです。Codex に任せた作業を確かめようと最新のログを選ぶと、別の会話と混線しました。指示文に目印を入れて探す方法も、ログの切り替わりで外れました。いまの運用では、作業フォルダで対象のログを特定します。

既定の起動先は同じタブの裏ペインですが、別タブを指定することもできます。下の画面では、Codex を右のタブに開いています。

アプリでは、公開リポジトリの CLI にある spawn がこの役を担います。完了マーカーだけでなく、ログの増分と編集ファイルの更新時刻も見ます。マーカーは、委譲する前に出力先を指示書で決めておくファイルです。

アプリ側に、エージェントの振る舞いを強制する仕組みはありません。「委譲は見える形で行う」とエージェント側のルールにも書いて、運用で守ります。見る人のいない自律ジョブ、大量に並列化する工程、介入の余地がない短い照合は例外です。

2. 観測から処置までの一本の線

状態を知る手段が増えても、画面ごとに違う判断を出さない設計を選びます。

あとからダッシュボードの「気づきカード」の並びを直しました。作業の停止や回答待ちを知らせるカードです。それまでは、外から届いた調整事項が、緊急でも参考情報でも同じ高さに並んでいました。

原因は、受け取った重大度を途中の処理で捨てていたことでした。いまは「誰を待たせているか」と「重大度」で順序を決めます。カードには根拠と、返す先や次の操作を添えます。

この並べ替えを、言語モデルには任せません。同じ状態なら同じ順序になり、上に出した理由を説明できる処理に置いています。

3. 機械が書く事実と、本人しか書けない言葉

テストの終了結果と、その結果をどう読んだかを分けて残します。

「報告インボックス」は、現在は対応が必要な気づきカードをまとめて見る入口です。実ログから事実を拾う処理が動いていなかった不具合は、あとから直しました。画面があっても、元の記録を読めていなければ役に立たないと分かった出来事です。

残す内容誰が確かめられるか
ファイルの変更、テストの結果、終了した事実記録を読める機械が確かめます。
何を発見したか、なぜその判断をしたか作業したエージェント本人の説明が要ります。

全セッション履歴の検索では、読み書きやテスト結果を機械だけで記録します。索引を作るときに言語モデルは呼びません。報告インボックスでは、対応が必要なものに絞って気づきカードを表示します。

「保存しました」という言葉だけで、成果物があるとは扱いません。説明を読んだ後も、ファイルとテスト結果で確かめる余地を残します。

4. 起動ごとに配る鍵

状態を知らせる権限は、どのエージェントの、どの起動なのかと結び付けます。

設計のとき、GitHub の公開プロジェクト stablyai/orca の認証方式を調べました。共通の鍵を端末へ渡す方式では、そこから起動した子プロセスまで書き込めてしまいます。鍵をタブごとに分けるだけでも、再起動前の通知が新しい作業へ届く余地が残ります。

委譲 CLI は、アプリの起動ごとに変わる認証トークンを自動で添えます。hook は、エージェントが終了や質問などを知らせる仕組みです。hook には、委譲 CLI のトークンとは別の権限情報を使います。

その権限情報（capability）は、次の 4 つに結び付いています。

  • タブ：どの端末の区画か。
  • provider：Claude、Codex、Grok のどれか（CLI の系統）。
  • launch_generation：同じタブで何回目の起動か。
  • app_instance：どの mycmux の起動か。

hook の受信処理は実装済みです。hook が失敗してもエージェントは止めず、認証できない通知では状態を変えません。

同じ利用者の権限で動くマルウェアや、同じ起動の中での嘘の自己申告までは防げません。この仕組みが守るのは、他のタブへのなりすましと、古い起動からの通知を分けるところまでです。

5. 責務の置き場所

画面を作り直すときも、動いている起動処理まで同時には置き換えませんでした。

以前のランチャーは、端末に 19 項目を描く文字メニューでした（現行のランチャーペインとは別のものです）。マウス操作が届かず、ペインが低いと上端の項目が流れて見えなくなりました。そこで、クリックで選べる現在のランチャーペインに置き換えました。

移したのは、表示と操作だけです。会話を識別する ID の発行や、作業フォルダの復元は、既存の起動処理に残しました。「続きから」の候補も、Ctrl+P の Resume と同じ一覧取得処理を使います。

設計の途中で、Resume、アイコン、起動カタログを既存の部品と気づかず、新しく作ろうとしました。新しい画面の話でも、まず使える部品を探し、それから責務を決めます。起動と、すでに開いているペインへの移動を、ひとつの検索窓には混ぜません。

この考え方が変わるとき

判断を変えるときは、理由を ADR（設計の決定記録）に残してから説明を更新します。たとえば、起動ごとの権限情報を意図したプロセスへ渡せないと実測できたら、配り方を考え直します。変えた結論と、変える根拠になった観測は、いつも一緒に残します。
